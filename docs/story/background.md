# 1. 왜 시작했나

::: lead
매번 같은 규칙을 다시 설명하는 일이 힘들어서 시작했고, 프레임워크 두 개를 거치는 동안 "무엇을 AI에게
맡길까"라는 질문에 "어떻게, 어디까지 통제할까"라는 질문이 더해졌습니다.
:::

## 첫 달: 매번 같은 설명

::: point Claude Code를 쓴 지는 넉 달입니다(2026년 10월 기준). 첫 달에는 기능을 하나씩 써 보며 무엇을 할 수 있는지 확인했습니다.
그러면서 몇 가지 불편이 보였고, 그중 가장 큰 것이 아래의 "매번 같은 설명"이었습니다.
:::

::: point 워크플로우를 만들 때마다, 모든 워크플로우에 따라다니는 공통 규칙을 매번 다시 설명해야 했습니다.
회사의 규칙을 적용하려고 넣는 프롬프트를 따로 모아 관리하게 됐습니다. 예를 들면:

- 사내망에서만 쓸 수 있는 환경이라는 점
- 외부 MCP 서버를 쓰는 데 제한이 있다는 점
- 참고해야 할 정보가 사내 어디에 있는지
- 지금 돌아가고 있는 환경이 무엇인지

(이 사이트는 공개 사이트라 특정 회사의 시스템이나 규칙은 쓰지 않고 이렇게 일반화했습니다.)
:::

::: point 이 경험을 에이전트가 계속 고정적으로 가져가고, 유지보수하고, 확장할 수 있게 하려고 프레임워크를 하나 만들었습니다.
:::

## 첫 번째 프레임워크: aise-workflow

::: point `aise-workflow`는 제가 미리 준 정보로, 제가 자동화하고 싶은 워크플로우의 시스템 프롬프트를 만들어 주는 프레임워크였습니다.
꽤 여러 개의 워크플로우를 이것으로 자동화했습니다. 이 과정에서 `CLAUDE.md`, `AGENTS.md`, 서브에이전트와
멀티 에이전트 같은 AI 에이전트 도구의 기본 개념을 익혔습니다.
:::

::: point 만드는 동안 겪은 일에서 네 가지 필요를 얻었습니다. {#four-needs}
토큰을 많이 썼고, 세션이 초기화되면서 작업물이 사라졌고, md 파일을 GitHub에서 형상 관리해도 새 세션마다
결과가 달랐습니다. 그래서 이렇게 정리했습니다.

1. **기억을 이어 줄 장치가 필요하다.**
2. **일관된 결과를 위해, 정확해야 하는 동작은 프로그램으로 만들고 LLM에 맡기지 않는다.**
3. **토큰 사용을 추적하고 통계를 낼 수 있어야 한다.**
4. **내가 만든 것을 다른 사람에게 배포할 수 있어야 하고, 배포된 뒤에도 같은 사용자 경험을 줘야 한다.**

이 네 가지가 각각 어디서 답해지는지는 이 쪽 맨 아래에 정리했습니다.
:::

::: point 그런데 만들어 놓고 보니 워크플로우는 결국 "정해진 동작을 하는 프로그램"이었습니다. 여기서 "무엇을 AI 에이전트로 처리해야 하나"라는 고민이 시작됐습니다.
워크플로우는 스크립트와 md 파일로 되어 있었지만, 하는 일은 늘 같은 순서의 같은 동작이었습니다. 그렇다면
그 부분은 굳이 에이전트일 필요가 있었을까 — 이 질문은 [3. 왜 조직인가](/story/why-organization)에서 뜻밖의
방향으로 결론이 납니다.
:::

## 두 번째 프레임워크: aise-development

::: point `aise-workflow`를 "소프트웨어로 개발하기 전에 프로토타이핑하는 도구"로 다시 정의하고, 그 워크플로우를 실제 소프트웨어로 개발하는 `aise-development`를 만들었습니다.
:::

::: point 저는 소프트웨어 공학을 공부했고 여러 프로젝트에 아키텍트로 참여했기 때문에, 그 일하는 방식을 프레임워크에 넣고 문서화하고 싶었습니다.
인터뷰, 요구사항 분석, 개발 방법론 정하기, QA 분석, 아키텍처 설계, 세부 컴포넌트·모듈 설계 같은 워크플로우를
`aise-development`에 넣었고, 꽤 많은 시간을 들였습니다. 나중에는 `aise-workflow`와 함께 움직이는 것 말고도
일반적인 소프트웨어 개발에 쓸 수 있게 확장을 생각하며 기능을 많이 더했습니다.
:::

::: point 기능을 더할수록 여섯 가지 문제가 생겼습니다. {#six-problems}
1. 풍부하게 만들려다 보니 스킬과 규칙이 수없이 늘었고, 곧 관리의 한계를 느꼈습니다.
2. 스킬, MCP 플러그인, 개발 방법론을 담은 시스템 프롬프트가 점점 커져서, 실제로 쓸 수 있는 컨텍스트 창이
   점점 줄었습니다.
3. 새로 나온 MCP 서버나 Claude Code 도구를 매일 익혀야 두 프레임워크가 강해졌고, 여기에 피로를 느꼈습니다.
4. 프로젝트마다 제가 중요하게 여기는 부분이 다른데, 어떤 때는 요구사항을 너무 짧게 모으고 성급하게
   만들었고, 어떤 때는 아예 시작하지 않고 정보만 모았습니다. 일관된 동작이 보장되지 않았습니다.
5. 개발 워크플로우를 자동화한 프레임워크라서, 동시에 진행되는 프로젝트 사이에 정보가 공유되지 않았고
   익힌 지식이나 방법론이 쌓이지 않았습니다.
6. 할루시네이션에 많이 시달렸습니다. 세운 정책이 제대로 동작하는지 확인할 방법이 없어서, 오랫동안 믿고
   있던 동작이 실제로는 이뤄지지 않았다는 걸 뒤늦게 안 적이 많았습니다.
:::

::: point 특히 자원이 늘 발목을 잡았습니다. 토큰이 매우 빨리 바닥났고, 도구만 바꾸고 정책과 기억은 유지한 채 프로젝트를 이어 가는 방법을 생각하게 됐습니다.
이 생각은 [6. 배포와 여러 도구](/story/distribution)로 이어집니다.
:::

## 개발하면서 느낀 점: 저는 감시자이자 승인자였습니다

::: point 소프트웨어를 시작하는 모양은 매번 달랐는데, Claude Code는 정보가 다 오기 전에 일에 착수하곤 했습니다.
어떤 때는 요구사항부터 최적의 설계안, NFR을 어떻게 맞출지까지 한 번에 떠올라 입력했고, 어떤 때는 피처의
집합으로 소프트웨어를 정의했고, 어떤 때는 이미 완성된 소프트웨어를 분석하고 아키텍처를 평가해 개선점을
뽑는 일이 먼저였습니다. 그런데 정보를 다 주지 않았는데도 바로 시작하는 경우가 있어서, 제가 줄 정보가
있었다면 토큰을 아끼고 하지 않아도 될 일을 피할 수 있었던 때가 있었습니다.
:::

::: point 개발 방법론도 최적의 것을 찾아서 하기보다, 프롬프트가 들어오면 어떻게든 무언가를 답하는 것처럼 느껴졌습니다.
:::

::: point 이게 중요한 이유는 제 자리 때문입니다: 저는 요구사항을 준 이해관계자이고, 결과를 최종 검수·승인하는 사람이고, 계획과 설계와 중간 산출물을 확인하는 감시자입니다.
한 번의 비용으로 제가 원하는 최상의 결과를 만들어야 하는 사람이기도 합니다.
:::

::: point 그런데 제가 개입할 수 있는 지점은 매우 좁았습니다. 워크플로우로 강제하면 느려지고, 풀어 두면 원하는 것과 먼 결과가 나왔습니다.
워크플로우로 강제하면 속도가 늦어지거나, 개발 흐름이 중복되거나, 개입이 너무 많아 마이크로 매니징이 되기
쉬웠습니다. 제한하지 않으면 제가 원한 결과와 너무 먼 무언가가 산출물로 나오는 일이 몇 번 반복됐습니다.
:::

::: point 그래서 "무엇을 AI 에이전트로 해결할까"에 더해 "어떻게 통제할까, 적절한 통제의 범위는 어디까지인가"가 가장 중요한 고민이 됐습니다. {#the-question}
이 질문에 대한 제 답이 aise-core입니다. 답의 줄기는 [3. 왜 조직인가](/story/why-organization)에서, 실제로
어떻게 생겼는지는 바로 다음 쪽 [2. 한눈에 보기](/story/at-a-glance)에서 보실 수 있습니다.
:::

## 네 가지 필요는 어디서 답하나

| 필요 | 답하는 곳 | 한 줄 |
|---|---|---|
| 1. 기억을 이어 줄 장치 | [5. 어떻게 유지하나](/story/how-it-is-kept) — 핸드오프, 부서 기록 | 끝난 일은 중요한 사실만, 못 한 일은 다음 세션이 같은 지식으로 이어 가게 기록합니다. |
| 2. 정확한 동작은 프로그램으로 | [3. 왜 조직인가](/story/why-organization), [5](/story/how-it-is-kept) — 훅과 스크립트 | 무엇을 프로그램으로 만들지는 Claude Code가 판단해 제안하고, 꼭 지킬 정책은 훅과 스크립트로 강제합니다. |
| 3. 토큰 추적과 통계 | [5. 어떻게 유지하나](/story/how-it-is-kept) — 토큰 모니터링 | 핸드오프를 만들다 시작됐고, 위임 구조의 고정 비용을 살피는 데 씁니다. |
| 4. 배포와 같은 사용자 경험 | [6. 배포와 여러 도구](/story/distribution) | 조직이 아니라 정책·훅·도구를 배포합니다. 같아야 하는 것(정책을 지키는 일)은 훅·스크립트·정책 문서가 맡고, 조직은 쓰는 사람마다 달라지도록 열어 두었습니다. |

::: warning 검토 질문 Q-1 (운영자 확인용 — 공개 전에 지웁니다)
여섯 가지 문제 중 1·2(스킬·규칙 관리, 프롬프트 비대)와 6(정책이 동작하는지 확인할 방법 없음)은 원문에 답이
있습니다(동적 도구 승인과 거버넌스 — part 8, 훅과 감시 목록 — part 23). 3(매일 새 도구를 익히는 피로),
4(프로젝트마다 들쭉날쭉한 동작), 5(프로젝트 사이 지식 공유·축적 없음)는 aise-core의 어느 부분이 답하는지
원문에서 직접 말씀하신 적이 없습니다. 짐작으로 채우지 않았습니다. 각각 무엇이 답인지(예: 3 → 자산참모가
도구를 조사·승인, 4 → PM의 계획과 완료 기준, 5 → 포트폴리오·회고·업무참모의 부서 간 조율) 확인해 주시면 표에
넣겠습니다.
:::
