# 7. 성장, 성과, 한계

::: lead
성장은 개별 역할이 아니라 조직이 할 수 있는 일(포트폴리오)과 공통 템플릿에 쌓입니다. 성과는 아직 TBD이고,
풀지 못한 것은 이 쪽의 한계 절에 모았습니다.
:::

## 성장: 역할이 아니라 조직에 쌓입니다

::: point 처음에는 "사람(역할)이 프로젝트를 하며 얻은 지식으로 스스로 발전하는" 모습을 생각했습니다. 그런데 그 방식은 버렸습니다. {#people-growth}
사람의 성장을 그대로 모델링했다면, 역할에 채용된 "사람"의 페르소나 파일이 계속 길어졌을 것입니다. 그건 고정 비용을
늘리는 방식이고, 그 페르소나가 모든 일에 다 필요한 것도 아닙니다. 그래서 과감히 방식을 바꿨습니다.
:::

::: point 대신 역할을 채용하고 해고합니다. 부서가 실제로 필요한 인력을 요청하면, 인사참모가 조사해 점검한 뒤 승인합니다. 역할을 부서마다 인스턴스로 쓰는 방식도 이 문제를 보완합니다.
같은 역할 정의를 여러 부서가 쓰고, 부서마다 필요한 도메인 맥락은 인사참모가 조사한 도메인 프로필로 그 부서의
기록에 따로 붙습니다. 사람 관리는 인사참모의 일이라 PM은 사람을 관리하지 않습니다 — 책임을 나눈 덕에 PM이
"사람의 마음과 성장"까지 떠안을 필요가 없어졌습니다.
:::

::: point 그럼 무엇이 성장인가: 프로젝트에서 얻은 지식으로 공통 템플릿이 강해지고, 포트폴리오에 올라 계속 쓰이는 역할이 생기는 것. 저는 이것을 성장으로 봅니다. {#what-growth-is}
- 포트폴리오: 다시 쓸 수 있는 역할·워크플로우·인사이트의 목록. "먼저 증명하고, 그다음 올린다"는 원칙으로 올립니다.
- 공통 기반과 템플릿: Meta 모드에서 강화합니다.
- 둘 다 프로젝트가 끝날 때의 회고에서 재료를 얻습니다.

생명주기 전체(회고 → 승격)는 참고 자료 [부서의 생명주기](/lifecycle)에 있습니다.
:::

::: point 정직한 현황: 구조는 열려 있지만, 실제로 올라간 것은 아직 적습니다.
2026-10-07 기준 포트폴리오에는 역할 5개가 있고, 워크플로우와 인사이트는 하나도 없습니다. 회고 기록은 2개입니다.

근거: `instance/portfolio/index.yaml`, `instance/retrospectives/` (기록 있음, 저장소 비공개).
:::

## 한계

이야기 중간에 나온 실패는 그 장치가 생긴 이유로 각 쪽에 두었습니다. 여기에는 아직 풀리지 않은 것만 모읍니다.

::: point 다른 도구에서는 검증 전입니다. 어댑터는 Claude Code용 하나뿐이고, 다른 사람에게 배포해 본 적도 아직 없습니다.
→ [6. 배포와 여러 도구](/story/distribution)
:::

::: point 독립 재검증이 아직 다 따라오지 못했습니다. 완료 항목 중 재검증된 비율을 늘리는 중입니다.
→ [5. 어떻게 유지하나](/story/how-it-is-kept#reverify)
:::

::: point 성장의 구조는 열려 있지만 실제 승격은 아직 적습니다(역할 5개, 워크플로우·인사이트 0개).
:::

::: point 수직 구조를 고르며 포기한 것이 있고, 의견이 갈릴 수 있는 선택도 있습니다: 같은 레벨 에이전트끼리의 토론을 허용하지 않는 것, 운영자가 참모하고만 이야기하는 것.
둘 다 자물쇠가 아니라 구조로 둔 선택이라 다시 평가하고 바꿀 수 있습니다. → [3. 왜 조직인가](/story/why-organization#given-up)
:::

::: point 아직 부족한 점 — **(운영자가 채울 자리)** {#still-lacking}
기억과 핸드오프, 토큰 추적, 배포에서 아직 아쉽거나 부족한 점은 콘텐츠 수정이 끝난 뒤에 보강하기로 했습니다. 짐작으로
채우지 않고 비워 둡니다.
:::
