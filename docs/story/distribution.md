# 6. 배포와 여러 도구

::: lead
배포하는 것은 조직이 아니라 정책·훅·도구이고, 조직은 쓰는 사람이 자기 취향대로 꾸립니다. 여러 도구에서
쓰는 설계는 되어 있지만, 지금은 Claude Code에서만 구현됐고 다른 도구에서는 검증 전입니다.
:::

[1. 배경](/story/background)의 네 번째 필요는 "다른 사람에게 배포할 수 있고, 배포된 뒤에도 같은 사용자 경험을
줘야 한다"였습니다. 그리고 토큰이 늘 모자라서 "도구만 바꾸고 정책과 기억은 유지하는" 방법도 생각했습니다. 이 쪽은
그 두 가지의 이야기입니다.

## 생각을 뒤집었습니다: 조직이 아니라 정책을 배포합니다

::: point aise-core를 만든 이유 중 하나는 다른 사람들도 잘 써 주면 좋겠다는 생각이었습니다.
:::

::: point 그런데 AI 에이전트를 써 본 경험으로는, 시스템 프롬프트를 어떻게 구성해도 똑같은 답을 주지는 않았습니다.
그래서 정책을 지키는 일은 훅과, 훅에서 실행되는 스크립트와, 정책 문서로 강제하고, 그 안에서 사용자가 자기 입맛에
맞는 조직을 꾸릴 수 있게 방향을 잡았습니다.
:::

::: point 조직 자체도 배포할 가치가 있지만, 배포 대상에서는 뺐습니다. 대신 정책과 훅과 도구를 "조직이 없는 상태로 시작"과 "기존 조직을 다시 쓰기"의 두 경우로 나눠, 쓰는 사람이 자기 선호에 맞게 바꿔 갈 수 있게 열어 두었습니다.
실제로 그렇게 되어 있습니다:

- 조직의 실제 데이터(어떤 부서와 역할이 있고 무엇을 했는지)는 aise-core와 분리된 별도 저장소에 둡니다.
- 새로 배포하면 조직은 비어 있는 상태로 시작합니다. 운영 모드에 처음 들어갈 때 꼭 필요한 기본 파일만 만들어지고,
  역할과 회고는 빈 채로 시작합니다.
- 그래서 같아야 하는 것(정책을 지키는 일)은 정책·훅·스크립트가 맡고, 달라도 되는 것(조직의 모양)은 쓰는 사람에게
  맡깁니다.

근거: `schema/instance/README.md`, `knowledge/decisions/workspace/instance-data-location.md`
"2026-07-08 — instance-data-lives-outside-repo-git", `governance/MODE_POLICY.md` "Org schema vs. org instance"
(기록 있음, 저장소 비공개).
:::

::: point 다만 "남에게 배포해 본" 적은 아직 없습니다. 지금 이 조직을 쓰는 사람은 저 하나입니다. {#not-yet-distributed}
새 사람이 빈 조직으로 시작하는 절차가 아직 다 갖춰지지 않았다는 점은 참고 자료
[Quick Guide](/quick-guide)의 첫 절에도 적어 두었습니다. 상태: **설계됨 · 일부 구현됨 · 다른 사용자로는 검증 전**.
:::

::: warning 검토 질문 Q-2 (운영자 확인용 — 공개 전에 지웁니다)
[1. 배경](/story/background)의 네 번째 필요는 "배포된 뒤에도 같은 사용자 경험"이었습니다. 원문(part 27)에서 말씀하신
것은 "정책은 훅·스크립트·문서로 강제하고 조직은 사용자 취향대로"였고, 이것이 네 번째 필요에 대한 답이라고 직접
말씀하신 적은 없습니다. 이 쪽은 "같아야 하는 것은 정책 층에서 보장하고, 조직은 일부러 달라지게 했다"로 이었습니다.
이 이음이 의도와 맞는지, 아니면 "같은 경험"은 아직 풀지 못한 한계로 7쪽에 둘지 확인 부탁드립니다.
:::

## 여러 도구: 설계됨 · Claude Code에서 구현됨 · 다른 도구에서는 검증 전

::: point 규칙은 특정 도구의 어휘 없이 씁니다. 도구마다의 "어댑터"가 규칙에 필요한 것을 제공합니다. {#adapters}
어댑터가 해야 할 일은 도구 중립적인 요구사항 목록 하나에 모여 있습니다 — 무엇을 점검하고, 막고, 상기시키고,
기록하고, 답해야 하는지. 점검 스크립트가 어떤 도구의 어댑터가 그중 몇 개를 갖췄는지 알려 줍니다. 이것이
[4. 원칙](/story/principles)의 의존성 역전입니다.
:::

::: point 지금 어댑터는 Claude Code용 하나뿐이고, 2026-10-07 기준 요구사항 39개 중 38개를 갖췄습니다(남은 하나는 "처음 필요할 때 만든다"로 미뤄 둔 비밀 정보 입력 기능).
다른 도구로 aise-core를 돌려 본 적은 아직 없습니다. 그래서 이 절 전체가 **검증 전**입니다.

근거: `governance/adapter_requirements.yaml`, `governance/adapter_check.py claude-code` 실행 결과 (기록 있음,
저장소 비공개).
:::

::: point 다른 도구에서 처음 aise-core를 열면, 그 도구의 에이전트가 먼저 어댑터 점검을 돌리고, 어댑터가 없으면 일을 시작하기 전에 운영자에게 "먼저 이것들을 만들자"고 제안하게 되어 있습니다.
저장소 맨 앞의 도구 중립 안내 문서(`AGENTS.md`)가 그렇게 지시합니다. 규칙을 읽을 수는 있어도 강제할 장치가 없는
도구는 규칙을 조용히 어길 수 있기 때문입니다.
:::

::: point 예전 두 프레임워크(`aise-workflow`, `aise-development`)는 다른 도구에서도 써 봤고, 그때 한계와 문제점을 파악해 두었습니다.
aise-core에서 그 경험을 바탕으로 가능한 문제를 미리 짚고 해결책을 준비하고 있습니다. 그 예가 어댑터라는 구조와
어댑터로 구현해야 할 요구사항 목록입니다.
:::

::: point 다른 도구에서 실험해 보고 찾은 것 — **(실험 후 채울 자리)**
실제로 다른 도구에서 돌려 보면 그 결과를 여기에 적습니다. 지금은 짐작으로 문제나 해결책을 쓰지 않습니다.
:::

## 이 사이트도 진행 중에 만들고 있습니다

::: point aise-core는 아직 끝이나 유지보수 단계에 가지 않았습니다. 순서상 이 사이트를 만드는 게 맞지 않을 수 있지만, 같이 진행해도 된다고 판단해서 시작했습니다.
"시작만 받고 끝은 모르는" 상태에서 확장할 수 있게 설계한다는 [4. 원칙](/story/principles)의 이야기와 같은
판단입니다. 그래서 이 사이트의 내용도 aise-core가 바뀌면 함께 바뀝니다.
:::
