# 4. 원칙

::: lead
원칙과 경계는 먼저 정하고, 기능은 열어 둡니다. 중심축은 OCP와 SRP 두 개이고, 나머지 원칙은 의도한 것과
자연스럽게 맞아떨어진 것을 나눠서 적습니다.
:::

[3. 왜 조직인가](/story/why-organization)에서 aise-core 같은 하네스도 소프트웨어이니 설계 원칙을 그대로
적용해야 한다는 깨달음을 말했습니다. 이 쪽은 그 원칙들입니다.

## 제가 설계하는 방식

::: point "원칙과 경계는 먼저 정하고, 기능은 열어 둔다." {#stance}
일찍 정하는 것은 원칙, 책임의 경계, 아키텍처상의 위험과 고객 요구사항의 위험입니다. 열어 두는 것은 세부 기능의
구현입니다.

저는 소프트웨어를 만들 때 원칙과 가치, 설계를 거의 90% 정하고 진행하는 아키텍트였습니다. 조금 부끄럽지만 UP 같은
방법론으로 배웠고, 스프린트 몇 번을 접목한 유사 애자일의 하이브리드 방식으로 많이 개발했고, 정통 애자일은
경험하지 못했습니다. 그래서 설계 초반에 아키텍처 위험과 요구사항 위험을 가장 먼저 뽑아 설계안을 만들고, 많은
부분을 열어 둔 채 시작합니다. "90% 정한다"와 "많이 열어 둔다"가 부딪쳐 보이지만, 정하는 것은 원칙이고 열어
두는 것은 세부 기능이라 둘은 같은 이야기입니다.
:::

::: point 이것은 습관이 아니라 경험에서 나온 방식입니다.
저는 시작과 끝을 함께 받기보다 시작만 받고, 많은 경우 나중에 기능 확장을 요구받았습니다. 그래서 설계 원칙이
무너지지 않고 소프트웨어의 책임 경계를 벗어나지 않는 한 확장할 수 있는 방식으로 설계했습니다.
:::

## 두 개의 중심축: OCP와 SRP

::: point 두 원칙이 중심인 이유는, 여러 사람과 함께 설계하고 개발하면서 가장 직접 맞닥뜨린 문제였기 때문입니다.
일반 법칙으로 하는 말이 아니라 제 경험입니다. 그래서 늘 신중하게 생각하는 부분입니다.
:::

::: point SRP(책임 분리) — 누가 무엇을 맡는지가 섞이지 않게 합니다. {#srp}
업무참모는 일, 인사참모는 사람(역할), 자산참모는 도구, 경영참모는 조직 자체의 개선을 맡고, PM은 부서 안의 일만
맡습니다. 기록마다 쓰는 주체가 하나이고, 도구가 그 경계를 막습니다. 인사참모를 따로 둔 것도 사람 관리에 SRP를
적용한 결과입니다([3](/story/why-organization)).

SRP를 지키려고 aise-core의 각 요소에 리팩토링을 많이 했습니다. 2026-09-30에 저장소 전체를 대상으로 SSOT·중복
감사를 했고(아래 SSOT 참고), 2026-10-01에 그 결과로 규칙 문서·스키마·어댑터를 다시 쓰고 참모 문서를 공통 형식으로
맞췄습니다. 결정 기록 124개 파일은 주제별 30개 파일로 옮겼고, 참모의 파일은 한 폴더로 모았고, 기록을 쓰는
주체가 자기 단위를 직접 커밋하게 바꿨습니다.

근거: aise-core 커밋 `e314f6d`, `8625c8d`, `31e90d2`, `f53429b` (기록 있음, 저장소 비공개).
:::

::: point OCP(확장에는 열고, 변경에는 닫기) — 끝을 알 수 없는 프로젝트라서 가장 중요한 원칙으로 삼았습니다. {#ocp}
aise-core도 시작은 했지만 끝을 알 수 없었습니다. 특히 기업을 모델링하기로 한 뒤로는, 회사가 문을 닫기 전까지
유지보수되고 계속 발전해야 한다는 특성을 생각해야 했습니다.

- 열어 둔 것: 새 도구(승인 목록에 추가), 새 역할(채용), 새 도구 환경(어댑터).
- 닫아 둔 것: 거버넌스와 책임 경계.

OCP를 적용한 곳은 두 가지, 조직의 발전과 사람의 발전입니다. 조직은 새 도구를 들이는 데 열려 있되 거버넌스는 강하게
적용하고, 프로젝트가 끝날 때마다 거기서 얻은 인사이트를 Meta 모드에서 조직의 기능으로 키웁니다. 사람의 발전이
실제로 어떻게 모델링됐는지는 처음 생각과 달라졌는데, 그 이야기는 [7. 성장](/story/growth-and-limits)에 있습니다.

참고 자료 [구조가 변경을 견디는 법](/structural-principles-ocp)에 OCP가 실제로 적용된 결정 사례가 있습니다.
:::

## 나머지 SOLID 원칙 — 정직하게 나눠서

::: point I(인터페이스 분리) — 의도해서 적용했습니다. 각 역할은 자기에게 필요한 도구만 받습니다.
역할 정의마다 `provisioning` 목록이 있고(예: 2026-10-07 기준 backend-engineer는 일곱 가지), 도구마다 사용 조건이
붙습니다. 출발점은 필요 없이 매번 불러오던 스킬과 MCP 서버였습니다([3](/story/why-organization)). 근거의 강도:
중간–강함.
:::

::: point D(의존성 역전) — 의도해서 적용했습니다. 제가 도구를 바꿔 쓰는 상황에 대처하도록 집요하게 지시했습니다.
규칙은 특정 도구의 어휘 없이 쓴 추상(어댑터 요구사항 목록)에 두고, 도구마다의 어댑터가 그것을 구현합니다. 새 도구가
생기면 규칙을 다시 쓰는 게 아니라 어댑터를 하나 새로 만듭니다. 근거의 강도: 구조로는 강함. 다만 어댑터는 아직
Claude Code용 하나뿐입니다([6](/story/distribution)).
:::

::: point L(리스코프 치환) — 설계해서 넣은 게 아니라 자연스럽게 맞아떨어졌습니다.
어댑터가 요구사항을 만족하는지 기계적으로 점검하므로(운영 모드에 들어갈 때마다 실행), 요구사항을 만족하는 어댑터는
다른 어댑터를 대신할 수 있습니다. 한계: 구현이 하나뿐이라 실제로 바꿔 끼워 본 적은 없습니다. 근거의 강도:
약함–중간. 과장하지 않습니다.
:::

::: point 역할 템플릿은 템플릿 메서드 패턴입니다. 처음 계획했던 "전략 패턴"은 정확히 맞아떨어지지 않았습니다. {#template}
공통 기본(모든 부서원의 기본 템플릿, PM은 PM 템플릿)이 뼈대와 공통 규칙("aise-core 회사에서 일하는 직원의 기본
자격")을 정하고, 역할마다의 정의가 그 위에서 달라지는 부분을 채웁니다 — 추상 기반과 구체 정의의 관계입니다.

원래 계획은 기본 속성을 추상 템플릿에 두고 도메인 지식을 전략으로 만드는 것이었습니다. 그런데 설계가 다른 쪽으로
갔습니다. 역할 정의에는 특정 부서의 도메인 배경을 넣지 않고, 역할이 어떤 부서에 처음 합류할 때 인사참모가 그
부서에 맞는 도메인 프로필을 조사해 그 부서의 프로젝트 기록에 남깁니다. 바꿔 끼우는 전략이라기보다, 부서마다 맥락을
주입하는 쪽에 가깝습니다.
:::

## SSOT — SOLID 밖의, 따로 세운 원칙

::: point 같은 내용이 여러 곳에 있다가 서로 어긋나는 일을 없앱니다. 2026-09-30 감사는 단순한 정리가 아니라 실제 기능 결함을 찾아냈습니다. {#ssot}
일곱 갈래로 나눠 저장소 전체를 읽은 감사에서 약 250건이 나왔고, 중복을 합치니 처음 정리에서 **실제로 강제가
잘못 동작하던 기능 결함 12건**, 운영자 결정이 필요한 사안 약 20건, 그리고 낡은 서술이나 끊어진 참조 같은 분명한
수정 약 140건이 남았습니다(후속 작업에서 기능 결함 몇 건이 더 추가됐습니다). 결정 기록을 주제별 파일로 옮긴
일도 이 감사의 결정 중 하나입니다.

근거: `knowledge/evaluation/2026-09-30-ssot-duplication-audit.md` (평가 기록, 저장소 비공개).
:::

## 레이어드 아키텍처

::: point 수직 계층은 레이어드 아키텍처를 모델로 삼았습니다. 조직을 모델링했기 때문만이 아니라, 관심사를 분리하고 유지보수성과 가독성을 얻으려는 선택이었습니다. {#layered}
대응 관계:

| 레이어드 아키텍처 | aise-core |
|---|---|
| 인접한 계층하고만 통신 | 운영자 ↔ 참모 ↔ PM ↔ 부서원, 건너뛰기 금지 |
| 상위는 하위의 내부를 모르고 인터페이스만 앎 | PM이 부서의 유일한 창구 |
| 계층 수 제한 | 실행 책임 줄은 두 단계까지, 위임도 두 단계까지 |
| 위로 갈수록 넓은 관심사 | 위로 갈수록 큰 시야(부서 → 부서 사이 → 조직 전체) |
:::

::: point 이름을 조직의 말로 붙였습니다(참모, 부서, PM, 채용, 해고). 처음 보는 사람도 구조를 짐작하기 쉽게 하려는 의도입니다.
설계 의도이지, 사용자 조사로 확인한 결과는 아닙니다. 이 사이트는 그래서 aise-core의 실제 이름 옆에 쉬운 말을
함께 적습니다(참고 자료 [용어집](/glossary)).
:::
