# aise-core on one page

::: lead
**An AI agent organization governance framework that fixes accountability and delegates judgment** — this is how aise-core is described for now (provisional definition).
:::

The operator has not yet settled what to call aise-core. The line above is the current description and will change if a better one is found.
Below is the whole site reduced to one page; each line leads to its chapter.

## The story in order

::: point **[1. Why it started](/en/story/background)** — Running several projects with AI agents makes cost rise fast and results uneven.
Two attempts produced four needs and six problems, and the question narrowed to "how, and how far, to control".
:::

::: point **[2. The answer: borrow a company's structure](/en/story/at-a-glance)** — Instead of controlling each action, judgment is delegated and accountability is bound by a company's structure.
The operator talks only to the staff, the ops staff forms departments, and a PM divides work among members and checks the results. From
instruction to report, in five sentences and one real request.
:::

::: point **[3. Principles](/en/story/principles)** — Principles and boundaries first, features left open. The two axes are SRP and OCP.
The constitution's five principles, the rest of SOLID and SSOT, layered architecture, what was designed differently for AI, and seven axes on
which it parts from the usual way.
:::

::: point **[4. Structure](/en/story/structure)** — Execution accountability is two levels, operator — department — member; the staff sit outside, each answering one question.
Organization chart and execution graph, three staff and the management staff, roles as classes, a department per project, two modes, templates
and instance.
:::

::: point **[5. How it is kept](/en/story/how-it-is-kept)** — The constitution sets principles, governance sets operating policy, and the adapter's hooks enforce only what must hold.
How policy becomes requirements and hooks, how the hooks are composed, and a written prohibition broken the next day.
:::

::: point **[6. Operation](/en/story/operation)** — The operator sets the mode and talks to the ops staff. Memory lives in a department's three record files.
How a department forms, delegation inside and between departments, a PM that starts fresh each time, handoff, waking a stalled delegation.
:::

::: point **[7. Verification and evaluation](/en/story/verification)** — Reports are re-checked against the actual output, screens in a real browser.
The organization is audited from real records, and cost is read with the execution graph. A real execution graph and evaluation output are shown.
:::

::: point **[8. Distribution and many tools](/en/story/distribution)** — What is distributed is policy, hooks and tools, not an organization.
Use with many tools is designed, implemented only for Claude Code, and **not yet tested** with other tools.
:::

::: point **[9. Growth, results, limits](/en/story/growth-and-limits)** — Growth accumulates in the portfolio and the common templates, not in individual roles. Results are still **TBD**.
The projects are in progress, so evaluation is premature. What remains unsolved is gathered under limits.
:::

## How to read this site

::: point Every chapter has three levels: one sentence, short key-point titles with a short explanation, and collapsed details.
To present or skim, read the titles and points. Opening a detail shows the background, problem, solution and the records behind it.
**Expand all / collapse all** at the top of a page switches at once, and printing includes the collapsed content.
:::

::: point The degree of confirmation is marked: designed · implemented · not yet tested, and record exists · operator's experience · hypothesis.
What has not been tried is not written as if it had been. Whether the basis is a record, the operator's experience or still a hypothesis is
marked too. The repository holding the records (aise-core) is private for now and to be published later, so paths are given without links.
:::

::: point It is no company's story.
It draws on the operator's working environment, but names no particular company's systems or rules, generalizing them, e.g. "an
intranet-only environment".
:::
