# 같은 문제를 두 번 처음부터 풀지 않으려면

[Philosophy](/philosophy)의 셋째 원칙 "조직은 지속적으로 성장해야 한다"가 실제로 어떻게 돌아가는지는,
여섯 단계를 한 바퀴 도는 순환으로 나타납니다.

## 여섯 단계

1. **채용(Recruitment)** — 필요한 역량이 없으면 새 역할을 만듭니다. 다만 만들기 쉽다는 이유로
   아무렇게나 늘리지 않습니다 — 기존 역할로 흡수할 수 있는지 먼저 확인하고,
   [뎁스-2 피라미드](/organization-model)를 벗어나지 않는지, 사유가 구체적인지 확인합니다.
2. **책임 부여(Assignment)** — 새 역할에게 역할과 책임을 명확히 부여합니다.
3. **협업(Collaboration)** — 업무 수행을 위해 실행 그래프를 구성합니다. 필요한 역할은 자유롭게
   협업합니다.
4. **보고(Reporting)** — 모든 업무 결과는 책임자에게 보고됩니다. 보고 체계는 조직도를 그대로
   따릅니다.
5. **피드백(Feedback)** — 리뷰와 피드백은 조직의 학습 과정이며, 다음 업무 방식과 지식자산에
   반영됩니다.
6. **지식자산화(Knowledge Accumulation)** — 새로 얻은 경험은 Workflow / Capability / Framework /
   Portfolio 같은 지식자산으로 쌓입니다. 그래야 다음에 비슷한 문제를 만난 다른 부서가 처음부터
   다시 풀지 않을 수 있습니다.

여섯 번째 단계는 다시 첫 번째로 이어집니다 — 쌓인 지식은 다음 채용 판단(기존 역할로 흡수할 수
있는가)의 근거가 되기 때문입니다.

::: info 결정 되짚어보기 — 왜 "역할 목록"을 미리 그리지 않았나
**문제.** 조직을 처음 설계할 때 흔한 유혹은 "이 프로젝트엔 어떤 역할들이 필요할지" 미리 조직도를
그려두는 것입니다. 그런데 실제 운영자의 업무 자체가 임베디드 SW, 펌웨어 시뮬레이션 툴링부터
일반 SW 엔지니어링, 그리고 CI/CD·자동화·서비스 개발까지 걸쳐 있는 500명 규모 조직 운영이라, 어느
한 도메인도 전체 범위를 대표하지 못했습니다.

**조사.** 미리 도메인을 정해 역할을 설계해 두면 어떻게 될지 따져봤습니다. 결정 문서의 결론은
명확합니다 — *"Pre-picking a domain would have overfit Phase 1 to a guess, contradicting §4.1
itself"*(도메인을 미리 고르는 건 Phase 1을 추측에 끼워 맞추는 것이고, §4.1 자체와 충돌한다).
미리 지어둔 구조는 나중에 운영자가 다시 풀어야 할 부채가 될 뿐입니다.
(근거: `knowledge/decisions/2026-07-07-recruit-on-demand-phase-1.md`)

**해결.** `instance/roles/`를 처음부터 **비워 둔** 채 시작했습니다. 역할은 실제 Operator 모드
업무가 조직에 아직 없는 역량의 공백을 드러낼 때만 만들어집니다 — 도메인별 하향식 사전 설계는
하지 않습니다.

**그래서 생긴 강점.** 역량 카탈로그가 추측이 아니라 실제로 벌어진 일에서 자라납니다. 그리고
이 원칙 자체가, 채용 주기(Lifecycle)를 다이어그램 연습이 아니라 실전에서 바로 검증하는 효과를
냅니다 — 이 사이트에 실린 모든 역할(frontend-engineer, devops-engineer 등)이 실제로 그렇게
생겨났습니다.
:::

## 부서 하나의 생애

이 여섯 단계는 조직 전체가 계속 도는 순환이고, 그 순환 안에서 부서(project) 하나하나는 각자의
생애를 따로 가집니다 — `draft → active → ended → closed`.

- **draft** — 요청이 아직 불분명할 때, 가볍게 대화하며 다듬는 단계입니다.
- **active** — 사용자가 명확히 승인하면, 실제 위임이 시작됩니다.
- **ended** — 사용자가 완료를 지시하면 이 단계로 넘어갑니다.
- **closed** — 지식누적 리뷰(회고 작성, 재사용 가능성 검토)까지 끝나야 완전히 닫힙니다.

::: info 결정 되짚어보기 — 부서는 이름을 바꾼 게 아니라, 의미가 바뀌었다
**문제.** 실무에서 두 가지 마찰이 드러났습니다. 하나는 오케스트레이터가 지정된 보고 체계를
건너뛰고 부서원에게 직접 연락하는 경향, 다른 하나는 조직이 한 번에 부서 하나당 업무 하나만
처리할 수 있다는 제약 — 이건 AI가 병렬로 일할 수 있다는 이 조직의 원칙(§2.5/§7)과 정면으로
부딪혔습니다.

**조사.** 처음 나온 해법은 "부서(부서)를 프로젝트로 이름만 바꾸자"였습니다. 그런데 이 제안은
곧바로 반박됐습니다 — 기존 §10.7/§10.8도 이미 부서 해산(해고, 조직개편)을 허용하고 있었으므로,
"영속성"은 애초에 '부서'의 절대 속성이 아니었습니다. 결정 문서는 진짜 구분점을 이렇게 짚습니다 —
*"under the old model, ending a department was 조직개편 — exceptional, user-approval-gated...
Under the new model, a department's end is the expected, routine outcome of its task
finishing"*(옛 모델에서 부서 종료는 예외적이고 사용자 결재가 필요한 조직개편이었지만, 새
모델에서는 업무 완료의 당연하고 일상적인 결과다).
(근거: `knowledge/decisions/2026-07-09-department-is-project-scoped-not-renamed.md`)

**해결.** '부서'라는 이름과 §10.2 규칙은 그대로 두고, **부서로 존재한다는 것의 의미**만
바꿨습니다. 부서는 어떤 역할-클래스가 실제로 실행돼야 하는 순간 형성되고, 업무가 끝나면 자동으로
해산됩니다 — 이 형성·해산은 결코 조직개편이 아닙니다. 대신 **조직개편은 이제 부서가 아니라
역할-클래스 카탈로그를 대상**으로 재정의됐습니다(기존 `instance/roles/*.yaml` 항목을 합치거나
쪼개거나 재분류하거나 퇴역시키는 일). "부서 두 개를 합친다"는 개념 자체가 사라진 겁니다 —
애초에 영속적인 단위였던 적이 없었으니까요.

**그래서 생긴 강점.** 부서가 일시적이 되고 역할-클래스에 고정된 헤드/스태프 구분이 사라지자,
"오케스트레이터가 보고 체계를 건너뛴다"는 원래 불만도 별도의 부서/스태프 디렉터리 분리 없이
자연히 해소됐습니다 — 부서의 PM이 업무참모와의 유일한 인터페이스라는 성질은 이제 디렉터리
구조가 아니라 **호출 중첩 구조 자체**로 강제됩니다.
:::

## Quick guide

**한 문장으로.** 조직은 여섯 단계(채용→책임부여→협업→보고→피드백→지식자산화)를 계속 순환하고,
그 순환 안에서 부서 하나하나는 필요할 때 생겨나 업무가 끝나면 자동으로 사라지는 **일회용
그릇**입니다.

**이 페이지를 직접 확인해 보려면**

1. `schema/README.md`의 "Phase 1 stance: recruit-on-demand" 절에서 "채용"과 "부서 형성"이
   서로 다른 사건이라는 구분을 직접 읽어보세요.
2. `instance/workspace/<프로젝트>/project-record.md` 상단의 `status:` 필드가 실제로
   `draft`/`active`/`ended`/`closed` 중 하나로 적혀 있는 걸 아무 부서에서나 확인할 수 있습니다.
3. 이 사이트(`aise-org-site`) 자신의 project-record.md도 같은 형식을 그대로 따릅니다 —
   지금 이 페이지를 쓰고 있는 부서도 예외가 아닙니다.

**다음으로.** 부서 안에서, 그리고 부서 사이에서 실제로 협업이 어떻게 조립되는지 →
[Collaboration Model](/collaboration-model).
